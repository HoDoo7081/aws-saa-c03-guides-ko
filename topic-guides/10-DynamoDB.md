# 10. DynamoDB — 서버리스 NoSQL

## 개념 이해

DynamoDB는 물품 보관표의 번호로 바로 물건을 찾는 보관소처럼, 키를 통해 빠르게 항목을 조회합니다. 서버를 직접 관리하지 않는 키-값·문서 데이터베이스이며, 관계형 조인을 전제로 한 SQL 앱을 변경 없이 옮기는 대상은 아닙니다.

## 핵심 개념

테이블은 항목(Item)과 속성(Attribute)으로 구성됩니다. 파티션 키는 데이터 분산에, 선택적 정렬 키는 같은 파티션 키 안의 정렬·범위 조회에 사용합니다. 특정 키에 요청이 몰리면 핫 파티션이 생기므로 **카디널리티와 실제 요청 분산**을 함께 고려합니다.

| 용량 모드 | 적합한 상황 |
|---|---|
| Provisioned | 예측 가능한 사용량, RCU·WCU와 Auto Scaling 관리 |
| On-Demand | 변동·불확실한 사용량, 요청당 요금 |

On-Demand도 파티션·계정·테이블 한도가 있으므로 핫 키나 모든 제한 문제를 자동 해결하지는 않습니다.

### 용량 계산

- 1 RCU: 4KB 이하 항목의 초당 강력한 일관성 읽기 1회 또는 최종 일관성 읽기 2회.
- 1 WCU: 1KB 이하 항목의 초당 쓰기 1회.
- 초과 크기는 단위별 올림. 트랜잭션 읽기·쓰기는 더 많은 용량 필요.
- 강력한 일관성 지원 여부는 테이블·인덱스·기능에 따라 다름. GSI에는 강력한 일관성 읽기를 사용할 수 없음.

| 기능 | 용도·함정 |
|---|---|
| DAX | DynamoDB 전용 인메모리 캐시. 기존 API와 호환성이 높지만 DAX 클라이언트 등 최소 코드 변경 필요 |
| Global Tables | 여러 리전에서 읽기·쓰기. 일관성 모드와 지원 리전 확인 |
| Streams | 항목 변경 피드, 24시간 보존, Lambda 트리거 |
| TTL | 만료 시각을 지난 항목을 비동기로 삭제. 정확한 만료 시각 삭제 보장 없음 |
| GSI | 다른 파티션·정렬 키로 조회, 기존 테이블에 추가 가능 |
| LSI | 동일 파티션 키·다른 정렬 키, 테이블 생성 시 정의 |
| Transactions | 여러 항목·테이블에 원자적 변경, 지원 범위·비용 확인 |
| PITR | 지정 보존 기간 안의 과거 시점으로 복원 |

TTL 삭제는 일반적으로 며칠 내 처리되며 “48시간 안에 반드시 삭제”라고 외우면 안 됩니다. Global Tables 복제 삭제에는 비용이 발생할 수 있습니다. 최종 일관성 Global Tables와 다중 리전 강력한 일관성 모드의 요건도 구분하세요.

항목 최대 크기는 **400KB**입니다. 큰 문서·이미지는 S3에 저장하고 DynamoDB에는 객체 키 등 참조를 저장합니다. 대표 서버리스 구조는 API Gateway → Lambda → DynamoDB입니다.

## 문제 유형

1. 글로벌 사용자들이 각 리전에서 쓰기 필요 → Global Tables.
2. 항목 변경 시 비즈니스 로직 실행 → Streams + Lambda.
3. user_id가 기본 키인데 email로도 조회 → GSI 검토.
4. 계좌 차감·입금을 모두 성공하거나 모두 취소 → Transactions.
5. 2MB 파일을 항목에 저장 → S3 + DynamoDB 참조.

## 빠른 복습표

| 단서 | 답 후보 |
|---|---|
| 키 기반 서버리스 DB | DynamoDB |
| 마이크로초 캐시 읽기 | DAX |
| 다중 리전 읽기·쓰기 | Global Tables |
| 변경 이벤트 / 자동 만료 | Streams / TTL |
| 기존 테이블의 다른 키 조회 | GSI |
| 여러 항목 모두 성공 또는 취소 | Transactions |
