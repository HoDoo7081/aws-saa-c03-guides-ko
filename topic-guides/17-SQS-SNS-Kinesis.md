# 17. SQS, SNS와 Kinesis — 메시징

## 개념 이해

SQS는 일이 쌓이는 우편함, SNS는 여러 구독자에게 전하는 방송, Kinesis Data Streams는 여러 소비자가 다시 읽을 수 있는 기록 흐름입니다. 중간 버퍼를 두면 생산자와 소비자가 서로의 처리 속도·일시 장애에 덜 의존합니다.

## 핵심 개념

### SQS

소비자가 메시지를 가져오는 큐입니다. 수신한 메시지는 **삭제되는 대신 가시성 제한 시간 동안 숨겨집니다**. 처리 후 삭제하지 못하면 다시 나타납니다. 처리 시간이 길면 제한 시간 연장·heartbeat를 검토하고 소비자는 멱등성을 갖춰야 합니다.

- Long polling: 최대 20초 대기로 빈 폴링 감소.
- DLQ: `maxReceiveCount`를 넘는 실패 메시지를 격리·분석.
- 보존 기간: 기본 4일, 최대 14일.
- 큰 본문: 현재 최대 본문은 1MiB이며 클라이언트·통합 지원도 확인. 원문의 256KB 한도는 오래된 수치.
- 큐 길이·인스턴스당 backlog로 워커 확장.

| 구분 | Standard | FIFO |
|---|---|---|
| 순서 | 최선 노력 | 메시지 그룹 안에서 순서 유지 |
| 중복 | 최소 1회 전달로 중복 가능 | 중복 제거 기능, 조건·시간 범위 확인 |
| 처리량 | 높은 처리량 | 배치·고처리량 모드·리전 할당량에 영향 |

FIFO라도 DB 쓰기 같은 외부 부작용이 자동으로 정확히 한 번 실행되는 것은 아닙니다. 실패 후 재수신 가능성을 고려합니다. 고정 300/3,000 수치만으로 현재 전체 상한을 판단하지 마세요.

### SNS와 팬아웃

토픽에 게시하면 구독된 SQS·Lambda·HTTP·이메일 등에 전달합니다. 구독 필터로 필요한 메시지만 선택할 수 있습니다. **SNS에 재시도나 내구성이 전혀 없다는 원문 설명은 잘못**입니다. 전달 재시도·DLQ와 FIFO 보관·재생 기능은 유형·프로토콜에 따라 지원됩니다.

여러 시스템이 독립적으로 복구·소비해야 하면 **SNS → 시스템별 SQS 큐** 팬아웃이 대표적입니다. 같은 SQS 큐에 소비자만 여러 개 두면 각 시스템이 모든 이벤트를 받는 구조가 아닙니다.

### 스트림·전달·기존 브로커

| 서비스 | 선택 기준 |
|---|---|
| Kinesis Data Streams | 여러 앱의 동일 스트림 소비, 보존 기간 내 재처리 |
| Amazon Data Firehose | S3·Redshift·OpenSearch 등 지원 목적지로 관리형 전달 |
| Amazon MQ | ActiveMQ·RabbitMQ·지원 AMQP/JMS/MQTT 등 기존 브로커 앱 이전 |

Kinesis 순서는 파티션 키·샤드 안의 조건을 고려합니다. 샤드 기반 모드와 On-Demand를 구분하고, 보존은 기본 24시간에서 최대 365일까지 설정할 수 있습니다. Firehose는 버퍼링·변환·전달 서비스이며 지연이 언제나 60초로 고정되지 않습니다. Amazon MQ도 기존 구성과 프로토콜 호환성 평가가 필요합니다.

## 문제 유형

1. 주문 폭주를 완충하고 워커가 자기 속도로 처리 → SQS + 워커 확장.
2. 주문 이벤트를 결제·분석·배송이 각각 처리 → SNS → 별도 SQS.
3. 어제 스트림을 두 앱에서 재처리 → Kinesis Data Streams.
4. 데이터를 S3에 적은 운영 부담으로 적재 → Data Firehose.
5. 동일 메시지 중복 처리 → 가시성 제한 시간·재시도·멱등성 확인.

## 빠른 복습표

| 단서 | 답 후보 |
|---|---|
| 완충·작업 분배 | SQS |
| 순서·중복 제거 | FIFO + 멱등성 |
| 빈 폴링 비용 | Long polling |
| 실패 반복 | DLQ |
| 다수 구독자·독립 내구성 | SNS → SQS |
| 스트림 재처리 | Kinesis Data Streams |
| 관리형 목적지 전달 | Data Firehose |
| 기존 브로커 프로토콜 | Amazon MQ |
