# 01. IAM — 자격 증명 및 접근 관리

## 개념 이해

AWS를 사무실이라고 생각해 보세요. IAM은 출입증과 출입 규칙을 관리합니다. 사용자(User)는 개인 출입증, 그룹(Group)은 부서, 역할(Role)은 잠시 빌려 입는 권한 조끼입니다. 정책(Policy)은 어떤 문을 열 수 있는지 정하는 규칙입니다. IAM은 리전에 종속되지 않는 글로벌 서비스입니다.

## 핵심 개념

| 구분 | 의미 | 사용 상황 |
|---|---|---|
| 사용자 | 장기 자격 증명을 가질 수 있는 개별 신원 | 기존 앱 등 필요한 경우. 사람은 연동·임시 자격 증명 우선 |
| 그룹 | 공통 정책을 적용하는 사용자 모음 | 팀별 권한 관리. 그룹·역할을 그룹 안에 넣을 수 없음 |
| 역할 | 수임(Assume)하면 임시 자격 증명을 받는 신원 | EC2, Lambda, ECS, 계정 간 접근, 외부 신원 연동 |

**컴퓨팅 리소스에 장기 액세스 키를 하드코딩하지 않습니다.** EC2는 인스턴스 프로파일을 통한 역할, Lambda는 실행 역할, ECS 앱은 태스크 역할을 사용합니다.

정책 JSON에서 읽어야 할 항목:

- `Effect`: Allow 또는 Deny.
- `Action`: 허용·거부할 API 작업. 예: `s3:GetObject`.
- `Resource`: 작업 대상 ARN.
- `Condition`: IP, TLS, MFA 등 추가 조건.
- `Principal`: 리소스 기반 정책에서 권한을 적용할 주체.

버킷의 객체 읽기 ARN은 `arn:aws:s3:::example/*`, 버킷 목록 조회 ARN은 `arn:aws:s3:::example`입니다. 작업마다 리소스 유형을 맞춰야 합니다.

### 정책 평가와 권한 상한

기본은 암묵적 거부입니다. 적절한 Allow가 있어야 하며, **적용되는 명시적 Deny는 Allow보다 우선**합니다. 다만 자격 증명 정책과 리소스 정책의 결합 방식은 계정과 Principal 유형에 따라 다르므로 모든 정책에서 Allow가 필요하다고 외우면 안 됩니다.

| 정책 | 대상과 역할 |
|---|---|
| 자격 증명 기반 정책 | 사용자·그룹·역할에 권한 부여 |
| 리소스 기반 정책 | S3 버킷·SQS 큐 등에 연결, 접근 주체 지정 |
| 권한 경계(Permissions boundary) | 사용자·역할 한 개의 최대 권한. 자체적으로 권한을 주지는 않음 |
| SCP | Organizations 멤버 계정의 권한 상한. 해당 계정 루트에도 적용, 관리 계정에는 적용되지 않음 |
| 세션 정책 | 특정 임시 세션의 권한을 더 제한 |
| S3 ACL | 레거시 접근 제어. VPC Network ACL과 다른 기능 |

### STS와 계정 간 접근

STS의 `AssumeRole`은 액세스 키 ID·비밀 키·세션 토큰으로 된 임시 자격 증명을 발급합니다. 유효 시간은 역할 설정과 호출 방식에 따라 다르며 역할 체이닝에는 추가 제한이 있습니다.

역할에는 **권한 정책(무엇을 할 수 있는가)**과 **신뢰 정책(누가 수임할 수 있는가)**이 있습니다. 계정 B에 역할을 만들고 A를 신뢰하게 한 뒤, A의 주체에 해당 역할을 수임할 권한을 부여하면 됩니다. 외부 업체에는 `ExternalId`로 혼동된 대리인 문제를 방지할 수 있습니다. ExternalId는 비밀번호처럼 비밀로 간주하는 값은 아닙니다.

### 직원 로그인과 계정 보호

- 여러 AWS 계정에 직원 SSO 제공: **IAM Identity Center**. 기존 IdP와 SAML 연동 가능.
- 앱 고객의 소셜 로그인: **Cognito**.
- 루트 사용자: MFA 활성화, 장기 액세스 키 지양, 일상 작업에 사용하지 않기.
- `aws:MultiFactorAuthPresent`: 임시 자격 증명의 MFA 맥락을 검사하는 조건 키. 모든 연동 로그인에 동일하게 적용된다고 가정하지 않기.
- 외부 공유 확인: IAM Access Analyzer. 미사용 권한 점검: 자격 증명 보고서·액세스 어드바이저.

## 문제 유형

1. EC2 앱이 DynamoDB에 안전하게 접근해야 한다 → 필요한 권한을 가진 **EC2 역할**.
2. 역할 권한은 맞는데 수임이 안 된다 → **신뢰 정책과 호출자의 AssumeRole 권한** 확인.
3. Allow가 있는데 Access Denied가 난다 → 명시적 Deny, SCP, 권한 경계, 리소스 정책 등을 확인.
4. 개발자가 역할을 만들되 정해진 권한을 넘지 못하게 한다 → **권한 경계 적용 강제**.
5. 기존 사내 계정으로 여러 AWS 계정에 접속한다 → **IAM Identity Center와 신원 연동**.

## 빠른 복습표

| 문제의 단서 | 먼저 검토할 답 |
|---|---|
| 임시·단기 자격 증명 | STS·역할 |
| 다른 계정 리소스 접근 | 대상 계정 역할 + 신뢰 정책 |
| 역할을 수임할 수 없음 | 신뢰 정책·AssumeRole 권한 |
| 조직 전체 권한 상한 | SCP |
| 사용자·역할 하나의 권한 상한 | 권한 경계 |
| 한 번 로그인해 여러 계정 사용 | IAM Identity Center |
| 루트 계정 보호 | MFA, 액세스 키 지양, 일상 사용 지양 |
