# 02. S3 — 객체 스토리지

## 개념 이해

S3는 파일을 맡기고 보관표를 받는 창고입니다. 파일은 객체(Object), 보관표는 키(Key), 창고는 버킷(Bucket)입니다. 일반 디스크·공유 파일시스템과 달리 API로 객체를 읽고 씁니다. 일반적인 객체 갱신은 전체 객체를 교체하는 방식입니다.

## 핵심 개념

### 스토리지 클래스 선택

**접근 빈도 → 복원 시간 → 최소 보관 기간과 요청 비용** 순서로 걸러냅니다.

| 클래스 | 접근·복원 시간 | 최소 보관 요금 기간 | 적합한 데이터 |
|---|---|---|---|
| Standard | 밀리초 | 없음 | 자주 접근 |
| Intelligent-Tiering | 기본 온라인 계층은 밀리초 | 없음 | 접근 패턴을 예측하기 어려움 |
| Standard-IA | 밀리초 | 30일 | 드물게 접근하지만 즉시 필요 |
| One Zone-IA | 밀리초 | 30일 | 재생성 가능한 단일 AZ 데이터 |
| Glacier Instant Retrieval | 밀리초 | 90일 | 드물게 읽는 아카이브, 즉시 조회 |
| Glacier Flexible Retrieval | 신속 1~5분, 표준 3~5시간, 대량 5~12시간 | 90일 | 분~시간 단위 복원 허용 |
| Glacier Deep Archive | 표준 통상 12시간 이내, 대량 통상 48시간 이내 | 180일 | 장기 보관, 긴 복원 시간 허용 |

복원 시간은 처리 옵션별 안내값이며 무조건 보장되는 완료 시각으로 해석하지 않습니다. Intelligent-Tiering의 선택적 아카이브 계층은 즉시 조회가 아닙니다. 128KB 미만 객체는 자동 계층 이동 대상이 아니며 작은 객체가 많으면 객체별 비용도 따져야 합니다.

패턴이 정해져 있으면 **수명 주기(Lifecycle)**로 전환·만료를 자동화합니다. 단기 데이터는 IA·Glacier 최소 보관 요금 때문에 Standard가 유리할 수 있지만 실제 총비용을 비교해야 합니다.

### 버전 관리·복제·잠금

- **버전 관리**: 덮어쓰기 이전 버전을 보존. 일반 삭제는 삭제 마커를 추가하므로 과거 버전이 즉시 사라지는 것은 아님.
- **MFA Delete**: 버전 영구 삭제 등에 MFA를 요구하는 추가 보호.
- **CRR / SRR**: 리전 간 / 같은 리전 내 복제. 양쪽 버킷에 버전 관리 필요.
- 기존 객체 복제: **S3 Batch Replication**. 규칙 활성화 이전 객체가 자동으로 모두 복제되지는 않음.
- **Object Lock**: 버전 관리와 함께 WORM 보존. 기존 버킷에도 활성화 가능.
- Compliance 모드: 보존 기간 동안 루트도 보호된 버전 삭제 불가.
- Governance 모드: 별도 우회 권한이 있는 주체가 우회 가능.
- Legal Hold: 해제할 때까지 보존. 해제 권한을 가진 사용자는 해제할 수 있음.

### 암호화와 접근 제어

| 방식 | 핵심 구분 |
|---|---|
| SSE-S3 | S3가 키 관리, 새 객체 기본 서버 측 암호화 |
| SSE-KMS | KMS 키 정책·사용 감사·권한 제어 |
| SSE-C | 요청마다 고객이 키 제공, HTTPS 필요 |
| 클라이언트 측 암호화 | 업로드 전에 암호화하여 AWS에 평문 미전달 |

S3 Bucket Key는 KMS 호출 비용을 줄일 수 있습니다. 기본 암호화 설정을 바꾸어도 기존 객체를 새 방식으로 다시 암호화하지는 않으므로 **Batch Operations** 등을 검토합니다. 전송 중 암호화는 TLS이며 `aws:SecureTransport=false` 요청을 버킷 정책으로 거부할 수 있습니다.

- **Block Public Access**: 공개 정책·ACL이 있어도 공개 접근을 차단할 수 있음.
- **사전 서명 URL**: 서명자의 권한과 자격 증명 유효 기간 안에서 임시 접근. SDK·CLI 방식은 최대 7일이지만 임시 자격 증명이 먼저 만료되면 URL도 먼저 만료.
- **CloudFront OAC**: S3 REST 원본 접근을 CloudFront로 제한.
- 서버 액세스 로그: 별도 버킷에 저장, 최선 노력 방식이므로 완전성·즉시 전달 보장 없음.
- CloudTrail 데이터 이벤트: 객체 API 접근의 주체 추적. 별도 설정·비용 고려.

### 성능과 이벤트

대용량 파일은 멀티파트 업로드로 나눠 전송합니다. 100MB 이상이면 검토하며 단일 PUT 한도를 넘으면 필요합니다. 전 세계 업로드 가속은 Transfer Acceleration, 다운로드 캐싱은 CloudFront를 검토합니다. 바이트 범위 GET은 필요한 부분만 읽습니다.

접두사별 요청 처리량 확장, 미완료 멀티파트 정리, S3 이벤트 → Lambda/SQS/SNS/EventBridge를 기억하세요. S3 로그를 SQL로 분석하려면 Athena를 검토합니다. S3 Select는 단일 객체 필터링 기능이지만 **신규 고객에게 제공되지 않습니다**.

## 문제 유형

1. 7년 보관, 거의 읽지 않으며 복원에 하루 이상 허용 → Deep Archive 검토.
2. 접근 시점을 예측할 수 없음 → Intelligent-Tiering. 정해진 시점 이후 접근 감소 → Lifecycle.
3. 규정상 관리자도 보존 데이터를 지울 수 없어야 함 → Object Lock Compliance.
4. 업로드된 이미지마다 썸네일 생성 → S3 이벤트와 Lambda.
5. 기존 객체가 복제되지 않음 → Batch Replication.

## 빠른 복습표

| 단서 | 답 후보 |
|---|---|
| 재생성 가능한 저빈도 데이터 | One Zone-IA |
| 아카이브인데 즉시 조회 | Glacier Instant Retrieval |
| 임시 다운로드 링크 | 사전 서명 URL |
| 키 사용 감사 | SSE-KMS |
| 전송 중 암호화 강제 | TLS + 버킷 정책 |
| 실수로 삭제·덮어쓰기 | 버전 관리 |
| S3 직접 접근 차단, CDN만 허용 | OAC |
| 데이터셋에 SQL | Athena |

> **원문 정정:** 객체 최대 크기는 기존 5TB에서 50TB로 확대되었습니다. Object Lock은 기존 버킷에도 설정할 수 있습니다. [공식 근거와 다른 정정 사항](../TRANSLATION-NOTES.md)을 확인하세요.
